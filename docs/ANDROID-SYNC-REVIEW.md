**Android sync and responsiveness review — 2026-11-17**

**Implementation update for 0.6.15/build17**

The accepted plan is now implemented for the release milestone. The shared link picker renders at most 18 rows; a 4,000-item browser fixture mounted in about 128 ms on the development PC. Checklist batches use one cloud reservation and one final cloud publication, with each acknowledged task receipt saved durably between them. Unchanged planner generations reuse their validated projection after fresh inventory checks.

Android adds a guarded headless shared projector using the supported [AndroidX JavaScriptSandbox runtime](https://developer.android.com/reference/androidx/javascriptengine/JavaScriptSandbox), revision-aware cache reads, prioritized requests, incremental background checks and explicit failure/denial handling. Supported devices can refresh the saved planner without an Activity or WebView; unsupported runtimes report their raw-cache-only fallback. REPORT-capable transports use sync deltas and bounded multiget batches. Page filters sync separately across devices; the shared Unscheduled sidebar can be resized and hidden.

The Windows form was also tested in the actual Electron host, including creation after a dragged Calendar range with the inspector open. Title entry and the visible native calendar popup passed; the reported obstruction remains unconfirmed. These are fixture checks, not physical-device startup, battery, thermal or Nextcloud Files crash measurements. The baseline investigation below is historical evidence for the changes, not a description of the new implementation. See [release evidence](RELEASES.md) for completed packaging and remaining acceptance work.

**Why Nextcloud Files is involved**

With Files sign-in, the path is:

`NextGlance UI → data worker → native bridge → Nextcloud Files service → server`

Files SSO delegates network requests as well as account authorization. Calendar/Tasks, Deck and planner-file requests can therefore exercise the Files process without opening its visible screen. The foreground connection is reused; background jobs have their own transport. Independent browser sign-in instead uses NextGlance's native HTTP transport. See [Nextcloud's SSO documentation](https://github.com/nextcloud/Android-SingleSignOn) and [service/IPC implementation](https://raw.githubusercontent.com/nextcloud/Android-SingleSignOn/main/lib/src/main/java/com/nextcloud/android/sso/api/AidlNetworkRequest.java).

The inspected upstream [Files provider](https://raw.githubusercontent.com/nextcloud/android/master/app/src/main/java/com/nextcloud/android/sso/InputStreamBinder.java) does not implement HTTP `REPORT`. Our SSO fallback is consequently limited to supported requests. The installed Files version is unknown. Switching sign-in alone would not enable delta sync: our direct-auth path also needs a delta reader and expanded validated REPORT support.

The reported “task created or recovered” error is emitted after a native task identity was verified, then later bookkeeping failed. Retrying must finish the saved request/link, not create another task. A generic network message does not prove the server was unreachable: provider/queue failures can receive the same classification. The Files crash cause remains unknown without its crash/ANR stack and version correlated with our request timeline.

**Recommended implementation sequence**

1. **Remove measured UI stalls first.** Build one pure-core record index and dependency reachability index per graph revision. Search that stable snapshot and render a bounded window of results. Revalidate the chosen relationship at submission. Avoid replacing/deep-cloning the whole reactive application state for progress-only updates. This follows Vue's guidance on [list virtualization, stable updates and shallow immutable data](https://vuejs.org/guide/best-practices/performance.html).

2. **Make editing a short, recoverable operation.** Give user edits priority over bulk reads. Replace repeated whole-planner synchronization with a bounded transaction/batch strategy that still establishes cloud reservations before native writes, records stable task identities durably, preserves concurrent-device checks, and repairs only unfinished metadata on retry. Separate checklist selection from a compact task editor with destination, dates and description. Do not remove idempotency safeguards to gain speed.

3. **Make background results directly usable.** Prototype one account-local, transactional, indexed read store consumed by launch, UI and future widgets. Background work must update usable records, not just raw response files. SQLite is a candidate; Room is optional in the existing Java host. The difficult boundary is executing the authoritative portable projections without a WebView or an untested second business engine. Resolve that with a small headless-projector experiment and the exact shared test vectors before committing to storage/runtime dependencies. Android recommends a [local repository as the UI read source](https://developer.android.com/topic/architecture/data-layer/offline-first). The Nextcloud Web host remains online-only.

4. **Reduce network and disk work.** Use collection-token equality in background jobs too, compare metadata without reading unchanged bodies, and resume bounded work after interruption. For capable transports, use `sync-collection` to obtain changed/deleted resource URLs and `calendar-multiget` to batch bodies. Apply changes and the new token atomically; expired tokens need a safe full-inventory fallback. Preserve original ICS and conflict validators. See the [CalDAV client guide](https://sabre.io/dav/building-a-caldav-client/) and [WebDAV Sync](https://sabre.io/dav/sync/). Keep Files SSO primary with its supported fallback; broader REPORT access needs an explicit provider/direct-transport solution. Deck has documented [ETag/304 and changed-index support](https://deck.readthedocs.io/en/stable/API/); share those conditional-read semantics across foreground/background.

5. **Finish lifecycle/retry behavior.** Current jobs have a 90-second application budget, cancel on foreground entry, and do not request immediate rescheduling after failure/stop. Keep progress checkpoints, use bounded backoff, and hand work over without restarting discovery unnecessarily. WorkManager is the recommended persistent-work abstraction, but replacing the existing JobScheduler would not repair its data pipeline. Keep jobs unique and constrained by connectivity/battery; no permanently running WebView/service. Android's [background-work guidance](https://developer.android.com/develop/background-work/background-tasks/persistent) and [battery guidance](https://developer.android.com/develop/background-work/background-tasks/optimize-battery) apply. [Periodic work](https://developer.android.com/reference/androidx/work/PeriodicWorkRequest) has a 15-minute minimum and can be delayed by Doze; an exact interval cannot be promised.

6. **Verify separately from packaging.** Measure cold launch to first usable cached page, durable restoration, fresh write permissions and final source freshness independently. Count queue/bind/HTTP time, response bytes, cache hits, parsed records and disk commits. Record job stop reasons and distinguish provider failure from network failure. Use [startup metrics](https://developer.android.com/topic/performance/issues/launch-time), [Perfetto/system tracing](https://developer.android.com/topic/performance/tracing), and WebView profiling to locate CPU, allocation, I/O and rendering costs. Proposed acceptance: cached browsing never waits for network; unchanged sync avoids body parsing; interrupted/retried task creation produces one task/link; closed-app sync changes appear locally on next open; picker work no longer blocks for seconds. Physical-device A/B measurements remain required for thermal and battery claims.

**Other requested behavior to specify before implementation**

- **Filters:** synchronize per account, scope and page, including My overview, and retain them across updates. This owner request supersedes FILTER-02's device-local policy. Specify migration/merge behavior and older-client compatibility first: current folder readers reject unrecognized planner settings/files. Do not inject new fields or let startup defaults overwrite cloud preferences. Immediately guard local pruning until authoritative organization restoration completes.
- **Unscheduled:** Overview places undated work in a hideable sidebar and omits it from timeline rows. Timeline offers the same sidebar optionally while retaining an explicit way to show undated rows for dependency editing. Calendar, Overview and Timeline share a fully hideable, resizable panel; hiding it must not consume a blank column. Extract one pure classifier first: Calendar currently overlooks dated linked bookings when classifying unscheduled work, unlike Timeline and the existing specification. Preserve undated semantics rather than invent dates; verify touch/keyboard resizing and Overview axis alignment.
- **Forms:** reproduce the Windows title/target issue in Electron; reuse the scheduling form's compact interaction pattern for checklist task creation, while retaining task-specific dates and native completion semantics.

These are queued requirements, not new implemented schema or parity claims. Update BEHAVIOR_SPEC, FEATURE_PARITY and vectors before the corresponding global changes.
