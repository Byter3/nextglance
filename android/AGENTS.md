## NO FULL BUILDS POLICY — Fast Verification

NEVER run `assembleDebug`, full assemble/bundle/release tasks, launch an emulator, or invoke `pnpm build`, `pnpm sync`, `apk:debug`, `cap sync` via a build wrapper or the current build-debug helper during regular coding/sub-agent iterations. Full UI/app builds require the owner's explicit request for a playable build at the end of a major milestone. This supersedes the earlier Phase 1 assembleDebug requirement. Do not hide a full UI build inside a unit-test task.

All state machines, parsing, validation and business rules MUST be in pure framework-independent core modules/classes or ViewModels with zero UI dependencies. Views only render state and emit intent. Inject platform effects and reuse shared core. A targeted local test MUST load `specs/TEST_VECTORS.json` and exercise actual production logic against those exact expectations.

Allowed native checks from `android/android/` (use `gradlew.bat` on Windows):

```text
./gradlew compileDebugKotlin
./gradlew testDebugUnitTest --tests "SpecificTestName"
```

The current native bridge is Java, not Kotlin: use `:app:compileDebugJavaWithJavac` as the native type/compile equivalent and `:app:testDebugUnitTest --tests "<fully-qualified-specific-test>"` for targeted local JVM tests; do not add Kotlin merely to manufacture that task. Android business services are currently portable JavaScript/TypeScript: targeted `node --test tests/<specific-test>.test.mjs` (including `tests/spec-vectors.test.mjs`) and `pnpm exec vue-tsc --noEmit -p tsconfig.json` are their fast logic/type checks, with no Vite/asset build. These are actual-stack equivalents of the owner's fast-verification policy, not permission for full app builds.

Use the already provisioned JDK/SDK and workspace Gradle cache. Native unit-test dependency compilation is allowed; APK/assets packaging is not. Do not run broad test suites repeatedly when a targeted test verifies the change.

Run meaningful tests for touched native operations, account isolation, SSO/transport capabilities, models/identity, cache restoration/revocation, first-sync adoption, revisions/merge/conflicts and lifecycle status. Use fixtures only; never reuse Windows credentials or mutate the owner's cloud. Existing fixture success is not physical SSO or cross-device verification.

When phone/tablet testing is separately authorized, record actual OS versions, app/provider versions and results in private evidence. No device verification claim without that test.

Report exact commands, passed/failed counts, changes and ambiguities for the current milestone. The orchestrator owns the shared parity ledger; provide evidence only for completed checks. During iterations explicitly distinguish fast checks from APK packaging. After an authorized final build, report the actual new artifact, manifest/version, signature, hash and packaged-asset verification; never present an old APK as newly verified. Physical-device evidence stays pending until that testing is authorized and performed.
